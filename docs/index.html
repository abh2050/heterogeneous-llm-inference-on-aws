01 · What we built

One API. Two compute pools. Two jobs.

A small, production-shaped service in AWS `us-east-2`, built to test whether interactive and background inference should share hardware.

MODEL

Qwen2.5 1.5B

The same BF16 model and vLLM 0.29.0 runtime ran on both nodes, so the hardware and workload placement were the changing variables.

FAST POOL

NVIDIA L4

An AWS `g6.xlarge` served 256-token chat prompts where first-token delay and smooth streaming matter.

BATCH POOL

Intel Sapphire Rapids

An AWS `c7i.4xlarge` served 2,048-token RAG prompts where completion matters more than interactive latency.

02 · Final output

Isolation rescued the user experience.

Interactive chat ran at 24 requests/s. Background RAG ran at 0.75 requests/s. Only the background route changed.

CHAT ALONE91 ms

p99 time to first token with no background work.

RAG SHARES GPU24.7 s

Long prefills pushed chat beyond capacity and created a large queue.

RAG MOVES TO CPU289 ms

Chat throughput returned close to baseline: 2,942 vs 2,971 output tok/s.

What this means

The CPU was not the faster inference device. It was valuable as an isolation tier: background jobs finished a little later so interactive users did not wait tens of seconds.

ConditionChat p99 TTFTChat p99 ITLChat output

Background RAG on GPU24,702 ms203.7 ms2,009 tok/s

Measured once per final condition. The router and benchmark clients shared the four-vCPU GPU host, so the exact improvement needs repeated trials on a cleaner topology.
