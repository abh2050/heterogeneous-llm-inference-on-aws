THE RESULT

Routing by service target protected chat latency

Can routing by service target, with interactive chat on a GPU pool and long-prompt RAG on a CPU pool, protect chat latency when both workloads arrive at once?

Result: A small amount of RAG traffic (0.75 RAG requests per second alongside 24 chat requests per second) on the shared GPU pushed chat p99 time to first token from 91 ms to 24.7 seconds. Routing RAG to the CPU pool brought it back to 289 ms, with chat throughput nearly unchanged.

RunChat p99 TTFTChat p99 ITLChat output tok/s
Chat alone on GPU91 ms30.2 ms2,971
RAG shared on GPU24,702 ms203.7 ms2,009
RAG routed to CPU289 ms112.0 ms2,942

(single run)

Chat runs at 24 requests per second, about 70 percent of the 34 requests per second sustained capacity at the SLO, so its throughput is lower than the 5,011 tok/s saturation figure.

The CPU pool was not faster or cheaper per token. It helped by isolating a delay-tolerant workload from interactive traffic.

Calculated cost was about $0.055 per million output tokens on the GPU pool (sustained chat capacity at the SLO) and about $0.78 on the CPU pool (TTFT-only chat capacity).

Hardware: GPU pool on an AWS g6.xlarge (NVIDIA L4, 24 GB). CPU pool on an AWS c7i.4xlarge (Intel Xeon, Sapphire Rapids) running vLLM's CPU backend with AMX.

Scheduler and memory tuning was tested on chat alone. The interference came from long-prompt prefill competing with chat decode on the same GPU, and separating the workloads removed it.

EVIDENCE BOUNDARIES

Measured, calculated, and still uncertain

MEASURED

Direct observations

TTFT, ITL, throughput, KV pool, engine comparison, router overhead, and mixed-workload behavior for this exact setup.

CALCULATED

Derived from measurements

Cost per million output tokens, speedup ratios, the 70% load point, and the 85× TTFT improvement.

ESTIMATED

Useful sanity checks

Roofline ceilings and theoretical compute or bandwidth explanations. These are not capacity commitments.

Limits you should say out loud

  • One small model and one precision were tested.
  • The final mixed-workload conditions were run once; variance is unknown.
  • CPU sweep runs were short, so their capacity values are upper bounds.
  • The router and two benchmark clients shared the four-vCPU GPU host.
  • Traffic stayed inside one VPC and one AWS region (`us-east-2`).
  • Autoscaling, multi-AZ failover, rolling releases, and sustained observability were not tested.
  • Prices are the experiment inputs, not current AWS quotes.

FURTHER READING

The papers behind the stack

  1. PagedAttention — explains the block-based KV memory design that made vLLM practical at high concurrency.
  2. Orca — introduced iteration-level scheduling, the foundation of continuous batching.
  3. Sarathi-Serve — studies chunked prefill and the trade between throughput and decode stalls.
  4. DistServe — separates prefill and decode so each phase can scale for its own bottleneck.
  5. Splitwise — explores phase splitting across heterogeneous hardware and its system-level tradeoffs.

BEYOND THE EXPERIMENT

Production gaps

This was a small experiment. A production deployment would also need:

  1. Repeatable installs with pinned containers for each pool.
  2. A sizing method that maps model, concurrency, and context length to pool layout and engine settings.
  3. Workload classification and routing rules tied to latency targets.
  4. Authentication, per-team quotas, and audit logs at the gateway.
  5. Dashboards for p99 TTFT, ITL, queue depth, and cost per million tokens.
  6. An offline install path for networks without internet access.
